# 《江城有灯》两项生活玩法 v1：剧情接入与验收

日期：2026-09-14。本文记录本轮实现、剧情接入与验收。**最终独立 Node 全量回归 612/612 通过**；代码、素材和状态机验收见文末，真实 UI 条目仍以主控实机报告勾选，不把设计时间预算当作真人测试结果。新玩法为「旧照里的位置」与「一口热的」，不是另起一套小游戏合集。

## 一、这一轮的闭环

| 玩法 | 谁请你做 | 主要操作 | 完成后的回应 | 与主线的关系 |
|---|---|---|---|---|
| 旧照里的位置 | 林婆婆 | 看真实场景构图的旧照，步行寻找观察区，再调整镜头对齐 | 阿遥拍下当下画面，回院给婆婆看，听一句生活往事 | 婆婆线完成后邀请，玩家可开始或稍后；老档不撤销已完成的关照安排 |
| 一口热的 | 蔡姨 | 读口味与收件纸条，分装食盒，选择步行/骑车/开车路线，分别向西巷陈姐与社区小许交接 | 陈姐接婆婆与自己的两份，小许接一盅藕汤；每份签收可见 | 新档在物资收齐之后、社区准备之前接入；老档已交付不追缴 |

共同原则：找到 → 判断/操作 → 亲手完成 → 当事人回应。不是点开图就算找到，不是装好就算送达，也不是靠被迫等待凑到 15 分钟。

## 二、旧照链路

### 首次游玩建议顺序

1. 送还收音机，保留原童画拼合与「一碗面的位置」回忆。
2. 在现时小院接 `photoIntro`，玩家明确选择开始或稍后，照片为可选探索，不撤销刚完成的婆婆线；旧信封和重开修理铺的真相仍在结尾。
3. 任务卡说明「看旧照，沿主巷找拍照的位置」。地图标的是可达观察区域，不直接把镜头自动摆到正确答案。
4. 玩家步行到区域后开启对景：照片与实时 3D 同屏，显示已认出的特征数；退出后位置和已完成照片保留。
5. 位置、方向、画面中的关键特征均达到容差后，玩家主动确认。取景框收起并回到现时的 3D 独白，不能仅到达范围就自动完成。
6. 完成后可回林婆婆的小院，`photoReturn` 做简短回应，记下 `photosReturned`；两处照片可以自由选择、补拍和回看，不变成真结局门槛。

### 画面/设计约束

- 照片要从实际 3D 场景与固定参考相机出发，再做泛黄、纸边、颗粒等年代感处理。生成图若与实际窗框、桥影、街口方向不同，不能拿来要求玩家对齐。
- 旧照至少两个固定特征，避免把会移动的居民、车辆、树叶作为必须对齐的点。
- 指引清楚区分「走到附近」和「抬起照片调整角度」。第一关容差宽于后续；不要求像素级精准。
- 对景时保留实时世界，无需跳到 CG 全屏。减少动态设置下停用抖纸、闪光、大幅镜头晃动，但对齐指示仍可读。
- 奖励画廊应来自有效对齐事件；回看收藏、读报、完成童画不替代新玩法的首次完成。
- 若角色在照片中遮住关键特征，可暂时采用观察相机而隐藏主角；退出必须恢复主角、用户视角与控制状态。

## 三、热食链路

### 首次游玩建议顺序

1. 保留 `chefIntro` 与三样物资领取：保温箱、密封饮用水、备用电池。物资各有来处，不能在分装台凭空生成。
2. 回蔡姨处核对后，保留旧灯回忆。不再以听完回忆直接视为「热食已送达」。
3. `foodPackIntro` 在现时摊前发生。纸条明确每位收件人的要求；先让玩家读，再让玩家配。
4. 分装错误具体指出「这一份不放葱」或「辣椒另放」，允许改单份；不清空全部劳动，也不使用笼统的「答错了」。
5. 成功分装只进入「已分装，待签收」。`foodReady` 后出现两处接力点和当前食盒数量：西巷陈姐接婆婆的热干面与自己的豆皮，社区小许接一盅藕汤。仍可步行或使用已有交通工具。
6. 两处先去哪边都可以。到达后需要停车/下车并逐份交接；西巷由陈姐接手、社区由小许接汤。`foodHandoff` 仅用于小许接藕汤这一场，不在西巷凭空出现小许。车轮经过接力半径不等于签收。
7. 三份全部签收后才完成新档 `chef` 安排，再接已有 `community` 对话、应急包和后续判断。社区提到「陈姐接了食盒，你的汤也到了」，而不是「蔡姨还等人取」。

### 有趣而不繁杂的部分

- 选择是记住人的偏好，不必引入“秒数耗尽就让老人饿着”的惩罚计时。
- 交通工具是到达方式，地图仍允许选择自己的路线；不能为完成配送强迫使用一辆特定汽车。
- 玩家临时下车、打开地图、和街坊问候后仍能继续配送；明确退出分装只退出 UI，不吞掉三样已领取物资。
- 干燥公共通道上的社区交接可以发生在雨前；不把任务终点设到真实江面/积水风险区。
- 傍晚叫热食、晚饭或分装，不叫过早。雨后阶段现有文本仅表示雨歇，不代表已到次晨。次晨过早由玩家明确选择「次晨番外」后开启，`foodPostlude` 才说「天晴了」；普通配餐复玩仍为「空盒练习」，别在夜景中宣称天亮。

## 四、已提供的对白模块

文件：`src/playful-life-dialogues.js`。

```js
import {
  PLAYFUL_LIFE_DIALOGUES,
  PLAYFUL_LIFE_SCENES,
  PLAYFUL_LIFE_COPY,
  playfulLifeLine,
} from './playful-life-dialogues.js';
```

- `PLAYFUL_LIFE_DIALOGUES`：`photoIntro`、`photoAligned`、`photoReturn`、`foodPackIntro`、`foodReady`、`foodHandoff`、`foodMorningHandoff`、`foodHandoffWest`、`foodReplay`、`foodPostlude`、`foodMorningAfter`。
- `PLAYFUL_LIFE_SCENES`：同名 key 的 `title`/`placeId`。其中 `photoAligned.placeId === 'photo-self'`，用无远端 NPC/POI 的当前地点标识，避免空 ID 被世界回退到附近 POI 或修理铺。
- `foodReady` 使用“西巷两份，社区一份”的跨轮通用口径；次晨交接用 `foodMorningHandoff`，次晨回蔡姨处用 `foodMorningAfter`，不再重复“明早见”。每组 2–4 句，单句少于 50 字；`time:'present'`，无 `cg`；`scope:'playful-life-v1'`，不占用旧 `draftId`。
- `playfulLifeLine(source,{foodMode:'pending'|'packed'|'delivered'})`：仅对下表三个现时句返回新的文本和新的音频 ID。默认、回忆、未知 ID 与未知状态均原样返回；原句对象不变。
- 新模块不自动加入冻结 `DIALOGUES`，避免将新增字幕误算为已录制的 v3 配音。主播放查找与 `presentationFor` 应显式识别新组；需要保留 `PLAYFUL_LIFE_SCENES` 的场景位置，不靠当前发言者来回切镜头。

## 五、存档与兼容

已经在 `freshState` / `loadState` 接入独立的 `photos` / `meals` 两个字段，分别调用 `normalizePhotoProgress` / `normalizeMealProgress`。不补完成、不清旧 flags；`photoTarget`、`photoInvited`、`photosReturned` 的前端邀请/回访由主控制器处理。

| 读入情况 | 行为 |
|---|---|
| 真正的新游戏 | 照片为主线之后的可选邀请；蔡姨线接完整热食，未做不自动标完成 |
| 旧档已 `granny` | 保留已完成关照安排与画廊；旧照为可选补玩，不把目标退回婆婆 |
| 旧档已 `chef` | 保留既有交付；热食提供空盒练习或下一次邀请，不要求重取三样物资 |
| 旧档已 `prepared`/`checked`/`ending` | 不倒扣任何旧旗标与剧情节点，不强迫在雨中回跑；适当阶段提供补玩 |
| 新档中途退出对景 | 已完成照片保留，未确认的当前角度不算完成；回到入口可重开 |
| 新档分装完成但未交接 | 持有待交接食盒，刷新后仍能去社区；不能丢食盒或凭刷新变已签收 |
| 新档已签收，再访问 | 用已送达回应，签收和奖励幂等 |
| 恢复结局分岔 | 恢复该分岔真实生活进度，画廊仍跨周目保留；不把未来完成记录倒灌到过去剧情 |
| 损坏字段/未知 ID/负数计数 | 回落该玩法默认值，不破坏主线、人物、声音设置和其他已有玩法 |

本轮保留 `granny` 的旧完成语义，旧照为可选延伸；新档 `chef` 在实际三份交接后设立，旧档已有 `chef` 不倒退。基础 `canAdvance` / `objective` 顺序不变，主控制器用实际 meal 完成事件与 `activeTask` 对接。自动化可证明合法迁移，不能据此捏造旧档未发生的相片时间、配送成绩或最短用时。

## 六、声音与冻结稿

`src/audio-director.js` 的 `voiceClipFor` 先查稳定 ID，再验证 `entry.text === line.text`。不匹配返回 `null`；现有 UI 文案为「这句暂以文字呈现」。

1. 新组全部是 `life-v1-*` ID，无录音时自然显示字幕，不拼接别人的声音凑句子。
2. 三个现时旧句的修订使用新 ID，去掉旧稿 `draftId`，不会错误播放“等人来取”的旧音轨。
3. 原 v3 回忆段、CG、字幕 cues 和已有音轨完全保留。不要为加一段当前分装操作去重写 CG 中的过去事件。
4. 后续录制应使用最终已验收的文本，男女主角分别录，其他角色沿用原音色；写入本地 manifest 后再核对 hash、时长、双主角查找和实际播放。
5. 录音与当前玩法测试不是同一件事。本轮未生成新 TTS，不应在交付中称为新对白已全部配音。

## 七、资产与 EdgeOne 闭包

`tools/edgeone-assets.mjs` 并非把整个 public 无差别上传：

- 会扫描 `index.html` 和所有 `src/**/*.js|css` 中以 `/media/`、`/models/`、`/textures/` 开头的完整字面路径。
- 新图使用完整路径字面量（例如 `/media/photo-match-v1-lane.webp`），且文件已存在于 public，扫描即可自动纳入；无需人工编辑图片文件白名单。
- 若使用 `` `/media/photo-match-v1-${id}.webp` `` 这类动态路径，则现有 literal regex 不会解析。需要将纯数据模块名加入 computed catalog 数组，或显式列举有限的照片 ID；不能用一个大目录全量兜底来掩盖遗漏。
- 新的独立 JSON manifest 不会仅因被代码 fetch 就自动递归收集里面所有图。应在脚本加入 `runtimeJSON`/`collect`，保留运行必要字段，排除生成请求与本机路径。
- 本轮 `PLAYFUL_LIFE_*` 为纯文本无图片路径、无 fetch，无需 EdgeOne 白名单变更。
- 检查命令（只读盘点，不上传）：`node tools/edgeone-assets.mjs --out output/qa/playful-life-assets`。
- 新图必须在 `asset-plan.json` 的 files 中出现，离线 prompt、参考原图、录屏和 `.env` 不能混入。单文件维持 25 MiB 以下，新增参考图建议按需加载，不加入首屏全部 preload。
- 当前云端已部署版不会因本地修改自动更新。本轮只完成代码接入与验收时，不宣称线上已有这两项；实际发布需另完成优化目录同步、闭包校验和部署验收。

## 九、发布前逐项验收

### 核心玩法

- [ ] 新档从接电话开始，不用控制台加 flag/传送，能一路做到旧照邀请、实际对齐、回访、分装、行驶/步行、西巷与社区三份签收、后续主线。
- [ ] 旧照全部目标在 `canWalk` 可行走区域；正常相机可以看见每个关键特征，不穿房、不需站在河里。
- [ ] 错位置/反方向/关键特征未齐时不判定成功；近似正确角度具有合理容差；确认按钮说明当前欠缺条件。
- [ ] 对景离开/打开地图/切视角/按 Escape 后可恢复；不遗留隐藏主角、锁鼠标、锁移动或悬空相机。
- [ ] 配错一份可以改单份；收件名、口味和状态始终一致，读纸条足够完成，不需要猜作者心思。
- [ ] 装好尚未送到、经过社区但未互动、途中关闭页面、取消对话，都不会误记签收。
- [ ] 分别实际步行、骑车、开车送达；路线可达、终点停车空间充足；在合理近距下才交接。
- [ ] 签收后任务、手账、街坊回应、场景食盒/纪念反馈相互一致；重复点击只记一次。

### 美术、输入、性能
